我同意你的判断。之前那个 Stage 5 的设计，确实把 **“Prime Agent 的实现细节”误当成了“Hello Harness 必须经历的一整套新基础设施”**，结果就出现了两个问题：

第一，`CodeRuntime / PythonRuntime / Persistent Runtime / Runtime State / Context Search...` 被横向铺得太开，像是在另起炉灶；第二，它没有充分继承前面已经做好的 `Harness Runtime / Tool Registry / Skills / Session / Events / Permission / Coding Agent`，这会破坏整套教程最重要的“逐步演进感”。

Prime Agent 自己其实也不是把前面的 Harness 全部推倒重来。它现在的设计明确是：**TypeScript host 继续拥有 agent loop、provider、session、child lifecycle、scheduling、usage accounting、recovery 等核心 Harness 能力；Python/IPython 只是模型面对的一层可编程控制面。** Extensions、skills、prompt templates、permission 等既有扩展面仍然继续存在。([GitHub][1])

所以，我认为 Stage 5 应该重构。

# 一、先重新定义 Stage 5 到底在解决什么问题

它不应该叫：

> 给 Harness 再造一个 Python Runtime。

真正的问题应该是：

> **我们已经有了一个成熟的 Coding Agent Harness，如何让模型更自由地“编排”这些现有能力？**

前面我们已经实现：

```text
Model
  │
  ▼
AgentRuntime
  │
  ├── Context
  ├── Session
  ├── Events
  ├── Permission
  ├── ToolRegistry
  │      ├── read
  │      ├── write
  │      ├── edit
  │      ├── bash
  │      └── git
  │
  ├── Skills
  ├── Extensions
  └── Workspace
```

这些东西一个都不能浪费。

Stage 5 应该做的是：

```text
                    Model
                      │
              原来：Tool Calling
                      │
                      ▼
                 AgentRuntime
                      │
                 Harness能力
```

演进成：

```text
                    Model
                      │
              Code as Action
                      │
                      ▼
             Programmatic Layer
                      │
                      ▼
                 AgentRuntime
                      │
        ┌─────────────┼──────────────┐
        ▼             ▼              ▼
      Tools         Skills        Subagents
        │             │              │
    Workspace      Extensions       Session
```

也就是说：

> **Code As Action 不是新的 Harness。**
>
> **它只是已有 Harness 上面新增的一种 Model → Harness 控制协议。**

这一下关系就顺了。

# 二、Tool Calling 和 Code As Action，本质上只是两个“控制平面”

Harness 收到后：



# 五、第 41 篇的问题不应该是“Tool 不够用了”

更准确应该说：

> **Tool Calling 在“单次能力调用”上很好，但复杂能力组合会越来越依赖模型多轮往返。**

例如我们已经有：

```text
glob
read
grep
```

现在模型要：

> 找出 src 下所有包含 `AgentRuntime` 且超过 300 行的 TypeScript 文件，然后只读取其中的 class 定义。

传统 Tool Calling 可能变成：

```text
Model
 ↓
glob
 ↓
Model
 ↓
read file 1
 ↓
Model
 ↓
read file 2
 ↓
Model
 ↓
read file 3
 ↓
...
```

大量：

```text
Model ↔ Harness
```

往返。

但如果已有这些能力：

```python
files = await glob("src/**/*.ts")

targets = []

for file in files:
    text = await read(file)

    if "AgentRuntime" in text and len(text.splitlines()) > 300:
        targets.append(extract_class(text))
```

那么：

```text
一次 Model Action
          ↓
一段程序
          ↓
多次 Harness Capability
```

这才是 Code As Action 真正解决的问题：

> **把能力编排权从 Harness Loop 的多轮 Tool Calling，部分交给模型生成的程序。**

不是“模型缺工具”。

而是：

> “模型已经会编程，为什么简单的循环、过滤、组合，还必须每次回到 LLM 做一次决策？”

# 六、这时候前面的 Tool Registry 反而变得更重要了

比如我们前面已经有：

```ts
interface Tool {
  name: string;
  description: string;
  schema: JSONSchema;

  execute(
    input: unknown,
    context: ToolContext
  ): Promise<ToolResult>;
}
```

Stage 5 不修改它。

新增：

```ts
class ProgrammaticToolBinding {
  constructor(
    private registry: ToolRegistry
  ) {}

  async call(
    name: string,
    args: unknown
  ) {
    return this.registry.execute({
      name,
      arguments: args
    });
  }
}
```

然后 Python 那边看到：

```python
await read(...)
await write(...)
await bash(...)
```

实际上跨桥调用：

```text
Python
 ↓
Bridge
 ↓
ProgrammaticToolBinding
 ↓
ToolRegistry
 ↓
Permission
 ↓
Tool.execute()
```

注意这里：

# Permission 也完全复用

例如：

```python
await bash("rm -rf dist")
```

不是 Python 自己执行 shell。

而应该：

```text
Python call
   ↓
Harness Bridge
   ↓
bash Tool
   ↓
Permission Gate
   ↓
Shell Executor
```

于是 Stage 4 做的：

```text
Permission
Hooks
Events
Workspace
Tool timeout
Error model
```

全部继续生效。

这才叫演进。

告诉模型：

这才是非常漂亮的继承路线：


```text

```

# 九、Subagent 才是 Code As Action 最重要的下一个演进

这也是我认为之前 Stage 5 没强调对的地方。

Code As Action 最重要的价值不是：

```python
for file in files:
```

这个当然有价值。

但真正把它升级到 RLM 的东西其实是：

> **LLM 调用本身也成为一个可编程函数。**

例如：

```python
auth = await agent(
    "分析认证模块",
    context=auth_files
)
```

这时 `agent()` 从哪来？

不应该重新实现 Agent。

它应该直接调用前面的：

```text
AgentRuntime
```

所以：

```text
Programmatic Environment
          │
          ▼
       agent()
          │
          ▼
     AgentRuntime
          │
          ▼
       Session
```

完整关系：

```text
                    Root AgentRuntime

                           │
                  generated program

                           ▼

                 Programmatic Layer

                           │
               await agent("...")

                           ▼

                   AgentSpawner

                           │
                           ▼

                   AgentRuntime

                    /            \
                   /              \
             Child Session     Child Context
```

这一下：

> Stage 2 的 Runtime

> Stage 3 的 Session

> Stage 4 的 Skills

全部重新发挥价值。

而 Prime Agent 当前也是这样设计：Python 中的 `rlm()` 只是薄桥，child execution、session tree、provider、lifecycle 等仍由 TypeScript host 管理。([GitHub][1])

# 十、所以 RLM 真正应该建立在三个已有抽象之上

我现在会把它总结为：

```text
RLM =
Programmatic Capability Calling
+
Programmatic Agent Calling
+
Persistent Working State
```

不是：

```text
RLM =
Python Runtime
+
Context Search
+
Compaction
+
一堆 Runtime 概念
```

三个核心支柱：

### 1. Capability as Function

以前：

```text
ToolCall
```

现在：

```python
await read(...)
await git.diff()
await skill(...)
```

复用：

```text
ToolRegistry
Extension
Skill
Permission
Events
```

---

### 2. Agent as Function

以前：

```text

```

现在：

```python
await agent(...)
```

复用：

```text
AgentRuntime
Context
Session
Events

```

---

### 3. State as Variable

以前：

```text
所有中间结果都必须塞 messages
```

现在：

```python
files = ...
analysis = ...
results = ...
```

变量可以保留中间计算结果。

这个才需要 persistent execution。

# 十一、这样 Persistent Runtime 就不再是“大章节”，只是第三个支柱的必要实现

为什么需要 persistent？

不是为了炫技。

假设：

```python
files = await glob("src/**/*.ts")

analysis = await asyncio.gather(...)
```

这一轮结束。

下一轮模型需要：

```python
len(analysis)
```

如果每次代码执行都是新的 process：

```text
analysis 消失了
```

所以才需要：

```text
Persistent Execution Environment
```

逻辑变成：

```text
Code As Action
      │
      ▼
需要跨 Action 保留程序状态
      │
      ▼
Persistent Execution
```

这就非常自然。

而不是单独发明：

```text
Persistent Runtime
Runtime State
Runtime Context
...
```

一大串概念。

# 十二、Runtime State 这个词我甚至建议删掉

直接叫：

```text

```

或者：

```text

```

就够了。



会严重增加认知负担。

# 十三、Context as Variable 也应该重新解释

之前说：

> Context as Variable = 模型可以搜索 context。

这个其实说窄了。

Prime Agent 对 RLM 的官方描述里，核心是把 context 当成变量，并让模型在 REPL 中对自己的 history、tools 和 subagents 做程序化操作。([Prime Intellect][2])

但对我们的 Hello Harness 教程，我不建议一上来实现一个复杂：

```python
context.search()
context.slice()
context.compact()
```

我们可以从非常简单的事情开始。

传统：

```text
Tool Result
 ↓
messages.push(...)
```

比如读了 10 个大文件：

```text
100KB
 ↓
全部进入 Context
```

Programmatic 模式：

```python
files = {}

for path in paths:
    files[path] = await read(path)
```

这时候：

```text
大文件内容存在 program state
```

模型最终只：

```python
important = select_relevant(files)

print(important)
```

只有必要结果进入模型下一轮。

于是：

> **Context as Variable 的价值不是“多一个 Context API”。**

而是：

> **并不是环境中获取到的每一份数据，都必须立即变成 LLM token。**

这个理解要重要得多。

# 十四、Context Search 也可以直接降级成一个案例，而不是 Harness 基础模块

比如这一篇：

这也符合整个 Hello Harness 的原则：

> **先让需求逼出抽象，而不是先给抽象找需求。**

```text
        │
        ▼
                 Harness Capability Layer
        │
   ┌────┼──────────┬──────────┬──────────┐
   ▼    ▼          ▼          ▼          ▼
 Tools Skills   Extensions Permission   Agents
   │
   ▼
Workspace / FS / Shell / Git
```

这里没有任何一层被浪费。

---

# 二十、然后 Stage 6 Continual Harness 也会变得更自然

因为到了 Stage 5：

Harness 已经对 Agent 暴露成：

```python
read(...)
git.diff(...)
skill(...)
agent(...)
```

Stage 6 再进一步：

> 除了“使用 Harness”，Agent 能不能“修改 Harness State”？

于是：

```python
await harness.memory.create(...)
await harness.skills.create(...)
await harness.prompt.update(...)
await harness.agents.create(...)
```

演进路线变成：

```text
Stage 4
Developer extends Harness

        ↓

Stage 5
Agent programs Harness capabilities

        ↓

Stage 6
Agent modifies Harness state
```

这个逻辑就非常顺。

而这也非常贴合 Prime Agent 对两个核心抽象的区分：

```text
RLM
= 如何执行 / 编排已有能力

Continual Harness
= 如何 CRUD prompts / memories / skills / subagents
```

Prime Agent 自己也明确要求把 RLM 保留给 runtime / kernel / native call interface，而 continual harness 是持续可编辑的 artifact/state layer。([Prime Intellect][2])

# 二十一、所以我现在会把整个项目的核心演进浓缩成 6 句话

```text
Stage 0
模型会回答。

Stage 1
模型会调用能力。

Stage 2
Harness 会管理模型如何运行。

Stage 3
Harness 能让模型操作代码世界。

Stage 4
开发者可以扩展 Harness。

Stage 5
模型可以编程组合 Harness。

Stage 6
模型可以持续改进 Harness。
```

其中 Stage 5 最关键的一句话就是：

> **不是给 Agent 一个新的 Python 世界，而是把我们前面辛苦构建的整个 Harness，变成一个模型可以编程调用的世界。**

我认为这样修正以后，`Code as Action` 才真正成为前 40 篇教程的“升维”，而不是旁边突然长出来的一条 Python 分支。
